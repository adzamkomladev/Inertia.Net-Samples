# Worker coordination

Worker registers TickerQ 10.4.0 with `TickerQ.Caching.StackExchangeRedis` 10.4.0. All workers in one deployment share the same Redis scheduler database and use distinct node identifiers. Aspire provides `worker1`, `worker2`, etc.; standalone containers use their hostname and process ID. MainApp and Realtime never register TickerQ.

TickerQ stores schedules and occurrences in Redis, atomically acquires jobs, sends node heartbeats, and recovers work held by dead nodes. The application's PostgreSQL `CronLeases` table additionally retains completed cron occurrences and missed-run catch-up state. Failed and interrupted occurrences release their lease and can retry; successful occurrences advance `LastRunAt`.

Set `TickerQ__RedisDatabase=1` by default. **Reserve that Redis database exclusively for one deployment's TickerQ workers.** TickerQ 10.4.0 prefixes some bookkeeping through `InstanceName`, but its persistence provider uses fixed `tq:*` keys. A cache prefix alone does not isolate two schedulers. App cache, realtime and rate limiting use the Redis database selected by `REDIS_URL` or Aspire's connection string, normally 0. Startup rejects using that same database for TickerQ. A different deployment on the same Redis server needs a different reserved database, or a separate Redis instance. This setup requires standalone Redis; Redis Cluster supports only database 0.

Redis uses a persistent volume and append-only persistence in both Aspire and Compose. Preserve the PostgreSQL and Redis volumes when restarting. Losing scheduler state can cause jobs to be scheduled again; the PostgreSQL occurrence guard still retains completion state.

The provider's default JSON metadata has a reported `TimeTickerEntity.Children` serialization problem. Worker supplies reflection metadata through `CronJsonContext` to retain non-public execution metadata. Its narrow converters preserve the exact round-trip timestamps used in Lua's optimistic concurrency check and accept the empty object that Redis Lua produces from an empty children array. Non-empty objects are rejected. Tests exercise the real Redis provider, two concurrent claims, timestamp precision, children serialization, and retry of a failed PostgreSQL cron occurrence. Recheck this adapter when upgrading TickerQ.

Coordination prevents concurrent claims; it does not promise exactly-once side effects after a crash. PostgreSQL queue jobs still use atomic database claims. View recording and other business operations retain their own deduplication/transaction rules. An email accepted by the provider immediately before a worker crash may be sent again on retry. Cron leases last 30 minutes and have no application heartbeat; keep handlers below that duration or add a renewable/fenced business-operation lease before introducing longer handlers.
