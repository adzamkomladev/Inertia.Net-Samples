# Multiple app replicas on one host

This sample derives from `ReactSqliteBlog` and retains React, ASP.NET Identity, EF Core 10, SQLite FTS5 and the existing feature set. HAProxy routes to three independent ASP.NET processes. They mount the **same local Docker volume** at `/data`, including `app.db`, `app.db-wal` and `app.db-shm`. A one-shot initializer applies migrations and WAL before any app process starts. Connections use foreign keys and a thirty-second busy timeout. Redis shares authentication keys, rate budgets and SignalR messages. S3 and optional Meilisearch remain shared external services.

This increases app and read concurrency on **one Docker host**. SQLite still permits one writer at a time. Do not spread these containers over hosts or mount the database through NFS/SMB. Separate local volumes would create separate databases. The Docker host and shared volume remain failure points. [SQLite's WAL documentation](https://www.sqlite.org/wal.html) explains both restrictions. The native library is pinned to SQLitePCLRaw.lib.e_sqlite3 3.53.3, and a runtime test verifies SQLite >= 3.51.3, which includes the documented multi-connection WAL-reset fix.

The existing worker's atomic `UPDATE ... RETURNING` claims remain safe across app processes. The new `CronLeases` migration records the scheduled occurrence and uses an atomic claim plus an ownership token: concurrent schedulers execute once, and completion survives restarts. Claims expire after thirty minutes; queue leases expire after five minutes. Neither renews. Keep tasks within the lease and make external effects tolerate retries. Wake signals and view buffers are local; other workers poll and a crash can lose buffered views.

Redis is required with `Replicas:Enabled=true`. All processes must share the same `Replicas__Namespace`, database file, analytics salt, service credentials and index. Separate samples use separate namespaces and cookie names. `REDIS_URL_DOCKER` selects the container URL; `.env.example` uses Compose Redis, while the local ignored `.env` retains the reference sample's configured external service credentials. Persist Redis, disable eviction for Data Protection keys, restrict access and encrypt key XML with a shared production certificate. Key loss invalidates cookies and email tokens.

HAProxy overwrites forwarding headers, provides cookie affinity for negotiated SignalR/long polling and exposes only its entry port. Production should terminate HTTPS and set `SECURE_COOKIES=true`. Live events trigger coalesced partial reloads of visible persisted data, avoiding snapshot ordering assumptions between independent publishers. Unsaved editors remain intact. Private SignalR notifications target their owner. Events are transient, with refresh prompts after reconnect; Redis failure fails readiness and denies rate-limited writes.

## Turso research

A remote Turso database is a potential route to app replicas on several hosts, but changing a connection string is insufficient for this sample. The [official .NET EF facade source](https://github.com/tursodatabase/turso/blob/main/bindings/dotnet/src/Turso.EntityFrameworkCore.Sqlite/Turso.EntityFrameworkCore.Sqlite.csproj) currently references EF Core 9.0.9, while this sample uses EF Core 10.0.12. That is a provider compatibility gap requiring a tested migration or a different data access layer. Turso/libSQL and the newer Turso engine also have different feature compatibility; verify the selected engine and driver.

A separate remote-provider prototype must validate Identity mappings, migrations, transactions, FTS5 and triggers, `MATCH`/ranking/snippet SQL, atomic queue and cron claims, error handling and freshness. `VACUUM INTO` backups currently write a local file; remote backups need replacement. Background claims and authentication must use an authoritative remote primary, not stale embedded replicas. This sample implements faithful local SQLite scaling and does not claim Turso or multi-host support.

See [DOCKER_ACCEPTANCE.md](DOCKER_ACCEPTANCE.md) for verification results.
